# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

EASYSTEM is an inventory/POS/service-orders/payroll/cash-reconciliation system for **Edward Accesorios** (4 locales). Astro (static site) + Tailwind v4 frontend; backend on **Cloudflare** (Worker + D1 + R2 + Better-Auth). It also runs with **zero configuration** in a LocalStorage demo mode when `PUBLIC_USAR_API` is not "true". The migration away from Vercel + Supabase is DONE: `cloudflare` was merged into `main` and the `supabase/` folder was removed (it stays in git history before the merge commit `cb78c4d`). The README is in Spanish.

## Backend actual (Cloudflare) — lee esto primero

Todo lo que dice más abajo sobre Supabase (ya eliminado del repo; solo queda como referencia histórica de las reglas), RLS, funciones RPC o migraciones `00NN` describe el sistema anterior: **las reglas de negocio siguen vigentes, pero su implementación ahora es esta**:

- **Datos**: D1 (SQLite). Esquema y triggers de seguridad en `migrations/0001_d1_schema.sql`; semilla (4 locales con ids fijos `…0001` a `…0004`, catálogo de modelos de teléfono) en `0002_seed.sql` (generada con `scripts/generar-seed.mjs`). No hay productos de ejemplo. Archivos en R2: `FOTOS_PUBLICAS` (se sirven sin sesión por `/api/archivos/publico/*`) y `FOTOS_PRIVADAS` (comprobantes de nómina y fotos de cuadre: solo con sesión y los mismos permisos que los datos).
- **API**: `src/pages/api/**`. Cada archivo lleva `export const prerender = false` y se construye con `conSesion`, salvo `salud`, `auth/*`, `archivos/publico/*` y `cuenta/estado` (`tests/server/rutas-protegidas.test.ts` lo exige). Servicios en `src/server/servicios/`, lecturas en `src/server/repos/`.
- **Seguridad (reemplaza a RLS)**: `src/server/authz.ts` — `cargarSesion` (cookie Better-Auth + perfil; usuario inactivo o con cierre forzado = 401), `alcanceDe` / `alcanceNomina` (locales accesibles según rol y suscripción vigente), `condicionAlcance`, `exigirRol`. Todo servicio recibe una `Sesion` y filtra por `Alcance`. Se comprueba primero el permiso y después la existencia (no se pueden tantear ids). `tests/server/matriz-roles.test.ts` prueba cada endpoint contra cada rol: **al agregar una ruta hay que agregarla a esa tabla**.
- **Auth**: Better-Auth con adaptador Drizzle (`src/server/auth.ts`), registro público deshabilitado, hash PBKDF2-SHA256 de 100.000 iteraciones (`password.ts`), clave mínima de 8. Las altas solo pasan por `crearUsuarioInterno` (lote atómico user + account + perfil). El primer administrador se crea con `node scripts/crear-admin.mjs --db local|remote` (clave aleatoria mostrada una vez, en la terminal del dueño; nunca por chat).
- **Atomicidad**: D1 no tiene transacciones interactivas, solo `db.batch` (atómico). Movimientos e unidades se registran en lote (`registrarMovimientos`: hasta 50 movimientos y 500 unidades; reintenta si dos ventas eligen la misma unidad). Los folios salen de la tabla `contadores`. Un lote sin sentencias da error en D1: protege los lotes vacíos.
- **Tiempo real**: cada escritura sube una versión en la tabla `cambios` (`sentenciasCambio` dentro del batch, o `avisarCambio` después, para catálogo, tasas y usuarios). `GET /api/cambios` devuelve solo lo que el rol puede ver; el cliente (`src/lib/sondeo.ts` + `realtime.ts`) consulta cada 10 s con la pestaña visible y actividad reciente y emite el evento `easystem:datos-cambiaron`. La API `alCambiarDatos` no cambió.
- **Cliente**: `src/lib/modo.ts` (`modoServidor`), `src/lib/api.ts` (errores en español; un fallo de red coincide con `esErrorDeRed`), `src/lib/auth.ts` y `src/lib/db/*.ts` hablan con la API. `inventoryService.ts` y `auth.ts` siguen siendo los únicos puntos de acceso a datos de las páginas.
- **Día de negocio**: el cuadre de caja se calcula en el servidor con `ZONA_HORARIA` (America/Caracas).
- **Scripts**: `scripts/crear-admin.mjs`, `scripts/cargar-controles.mjs` (carga validada y reanudable del inventario real del Local de controles desde `datos-controles/`, ignorada por git), `scripts/generar-seed.mjs`.

## Architecture (reglas de negocio; los detalles de Supabase/RLS/SQL son del sistema anterior)


### The dual-mode data layer is the core design constraint

`src/lib/inventoryService.ts` and `src/lib/auth.ts` are the **only** allowed entry points for data access. No page or component should import `src/lib/db/*.ts`, `src/lib/mock-data.ts`, or `src/lib/supabase.ts` directly — always go through those two files. They each internally decide, at call time, whether to talk to Supabase (via `src/lib/db/`) or to LocalStorage (seeded from `src/lib/mock-data.ts`), based on whether `src/lib/supabase.ts` was able to instantiate a client from env vars.

Consequences of this that are easy to miss:
- The LocalStorage fallback only works in the browser, so **every page fetches its own data from a client-side `<script>` tag** ("self-fetching" pattern) rather than in Astro frontmatter. Don't move data fetching into frontmatter — it would break the fallback and offline behavior.
- `productos.stock_actual` is derived, never written directly. It only changes through `movimientos_inventario` rows (DB trigger `aplicar_movimiento_inventario`, mirrored in JS for the LocalStorage path). A POS sale is internally one or more `SALIDA` movements — if you need to touch stock, add a movimiento, don't write stock directly in either backend.
- Sales are **not transactional across line items**: lines are processed sequentially, so a sale can partially succeed (early lines committed, a later line rejected for insufficient stock). A true transactional sale needs a Postgres RPC function — this doesn't currently exist.
- When Supabase is configured, `inventoryService.ts` caches every successful read (productos/modelos/movimientos) to LocalStorage and serves that cache on network failure or `navigator.onLine === false`. Sales made offline queue in `easystem:cola-sync` and retry automatically on the `online` event; `ConnectionStatus.astro` (in the Header) shows sync status and a manual "Sincronizar" button. This is best-effort, sequential, and has no conflict resolution — it assumes a single till, not concurrent terminals.
- **Camera barcode scanner** (`src/components/CamaraEscaner.astro`, using `html5-qrcode`, lazy-imported on open): a single reusable modal, not a per-page component. Any element with `data-abrir-escaner` opens it (global click delegation); on a successful decode it dispatches `window` event `easystem:codigo-escaneado` with `{ detail: { codigo } }` and closes itself. Consuming pages (`ventas.astro`, `productos/index.astro`) just add a trigger button and a `window.addEventListener('easystem:codigo-escaneado', ...)` — no direct coupling to the component. Follow this same event-based pattern for any future scan targets instead of importing the modal's internals. It reads **QR and product barcodes** (EAN-13/8, UPC-A/E, Code 128 only, native `BarcodeDetector` when the phone has it, no scan box: the whole frame is analysed). Gotcha fixed: `iniciarCamara` must take its session token AFTER `detenerEscaneo()` (that call bumps the token); taking it before made the camera never start (black view stuck on "Solicitando acceso…"). Tested end-to-end in the preview by faking `getUserMedia` with a `canvas.captureStream()` showing a generated QR (return a FRESH stream per call: the library stops the first one while listing cameras).

### Auth and roles

Six roles (`Rol` in `auth.ts`, enum `rol_usuario` in Postgres; hierarchy administrador > gerente > encargado > vendedor/tecnico — see "SaaS subscriptions and role hierarchy" below): `administrador` and `gerente` (global: all locales), `encargado` (manager of ONE local), `vendedor` (cashier of one local) and `tecnico` (service technician of one local). Everyone but administrador/gerente has a `local_id` (see "Multi-local" below). The permission helpers are `esAdministrador` / `esGerencia` (administrador + encargado) in `auth.ts`; pages restrict by role with `DashboardLayout`'s `roles={[...]}` prop and nav links by `roles` in `navLinks.ts`. Role storage mirrors the same dual-mode pattern — `perfiles` table in Supabase, or a simulator in LocalStorage — both behind `src/lib/auth.ts`. Every page requires a session (`/login`); admin-only routes redirect vendedores to `/`. This guard (`protegerPagina`) runs client-side, called from `DashboardLayout.astro`, and is what every page layout relies on — it is **not** a substitute for server-side RLS if stronger protection is ever needed. Role also gates UI visibility client-side: purchase price column in Productos, Reportes, and Usuarios are hidden/blocked for vendedores.

**There is no public sign-up** — the system is internal (owner + a few employees). `/login` only logs in. Account creation is admin-only and is enforced in the database, not just the UI: migration `0004` adds a `BEFORE INSERT` trigger on `auth.users` that rejects any signup whose email wasn't pre-authorized (row in `usuarios_autorizados`, valid 10 min, consumed on use). `registrarUsuario` in `auth.ts` does it in two steps — admin inserts the authorization (RLS: admins only), then creates the account with an isolated client. Don't reintroduce a self-registration path, and never trust `raw_user_meta_data` for roles (the perfiles trigger always creates `vendedor`; admins promote via `update perfiles`).

First Supabase admin must be bootstrapped manually: insert the email into `usuarios_autorizados` via the SQL editor, create the user in Authentication → Users → Add user within 10 minutes, then `update public.perfiles set rol = 'administrador' where email = '...'`. After that, admins create more users from `/usuarios`.

### Directory map

- `src/lib/db/` — per-table Supabase access (productos, modelos, movimientos, locales, ventas, tasas, devoluciones, ordenes). Only called from `inventoryService.ts`.
- `src/lib/navLinks.ts` — sidebar links, each with a minimum required role.
- `src/lib/catalogo-modelos.ts` — master list of phone models (brand → models), the single source for both LocalStorage (`mock-data.ts` appends them, and `leerDB` back-fills missing ones into existing browsers) and Supabase (`migrations/0005_catalogo_modelos.sql` is **generated** from it — regenerate when the list changes). Products link to models **by model name**, so never rename an existing entry; add new ones instead.
- `src/types/database.types.ts` — types mirroring the SQL schema.
- `src/stores/theme.ts` — dark/light theme via nanostores + localStorage, applied class (`.dark` on `<html>`) before first paint to avoid flash.
- `src/utils/{format,csv,dateRange}.ts` — shared formatting/export/date-range helpers.
- `supabase/schema.sql` — full reference schema; `supabase/migrations/` — the actual migration history (`0001_init`, `0002_perfiles`); `supabase/seed.sql` — sample data.

### Product management (administrador/gerente; the encargado creates/edits products too — see "Ingreso de mercancía")

Productos has management tools implemented as `<dialog>` components in `src/components/productos/` (`FormularioProducto`, `ImportadorCsv`; stock entries moved to the Ingreso de mercancía page). They follow the same event convention as the camera scanner: the page dispatches `easystem:abrir-producto` / `easystem:abrir-importador`, and the dialogs dispatch `easystem:productos-cambiaron` after saving so the page reloads its list. Each dialog re-checks the role itself.

- **Nombre de producto único** (`exigirNombresLibres` en `servicios/catalogo.ts`; demo: `exigirNombreLibreLocal` en `inventoryService.ts`): no se puede crear ni renombrar un producto a un nombre que ya existe (se compara sin mayúsculas, acentos ni espacios de más: `normalizarNombre` de `utils/altaRapida.ts`). Rige en crear, alta rápida (todo o nada), importador y edición; el rechazo es 409 `nombre_repetido` y dice cuál es (con su referencia) y que para sumarle unidades se use «+ Stock»; repetir un nombre dentro de una misma lista es 400. En edición solo se revisa si el nombre cambia, así que los duplicados que ya existían (p. ej. CRV-005 / CRV-007) se pueden seguir editando; NO se fusionan solos (pueden tener stock, unidades e historial). Tests: `tests/server/nombre-repetido.test.ts`, `tests/cliente/nombre-repetido.test.ts`.

- **Deleting products entered by mistake** (administrador/gerente only; encargado/vendedor get 403): Productos → **Seleccionar** → tick products → **Eliminar seleccionados** → type ELIMINAR. `POST /api/productos/eliminar-lote` (`eliminarProductosLote` in `servicios/catalogo.ts`, up to 100 ids; `eliminarProducto` for one) deletes the product with its units, movements, stock in every local and compatibilities (FK cascade). **Safety rule**: a product with ANY history is NOT deleted (409 `producto_con_historial` / listed in `bloqueados`): any movement other than ENTRADA (sale, traslado, baja, adjustment) or any unit not DISPONIBLE; those must leave the stock with a baja (Mercancía → Descargo). Unknown ids are ignored. Demo mode applies the same rule (`inventoryService.eliminarProductos`). Reference/unit counters are not rewound (gaps are fine).

- **Roles are enforced in the database too** (migration `0006`): products/models/compatibilities are writable only by `administrador`; any authenticated user may insert `SALIDA` movements (sales), but `ENTRADA` is admin-only. The stock trigger is `SECURITY DEFINER` so a vendedor's sale can still decrement stock. Column-level hiding of `precio_compra` is still UI-only.
- **Alerts**: `stock_minimo = 0` means "not tracked" — it never alerts (`esStockBajo` in `utils/format.ts`, mirrored by `vw_productos_stock_bajo`). Newly loaded products use 0 on purpose.
- **Barcodes**: products without a factory code get an internal EAN-13 with prefix `20` (`utils/codigos.ts`; same rule as SQL `ean13_interno`). Never hand-edit the algorithm in only one place.
- **CSV import**: `lib/importador.ts` is pure (parse → validate → *plan*); `inventoryService.importarProductos` applies it. Stock is never written directly: new stock enters as an `ENTRADA`, and a differing stock in the file becomes an `ENTRADA`/`SALIDA` "ajuste". Supabase applies it in batches; it requires a connection (not queued offline).
- **Forros per model** are generated by migration `0007`, and general (non-model) chargers/cables/popsockets by `0008` (both SQL, idempotent, skip names that already exist) — they are *not* in `mock-data.ts`; the LocalStorage demo keeps its small sample catalog, so test bulk loading there with the import template. Their sale prices are placeholders to be corrected via CSV import.
- **Price lists** (data migrations, idempotent, run in the SQL editor): `0017` sets the Local Accesorios sale prices (forros silicona $6 / antigolpes $7 / transparente $6; cargadores and cables $5–15 by type/wattage; popsockets $2–4 — it only touches `precio_venta`, and leaves MagSafe forros alone). `0018` creates, per phone model, *Vidrio blindado $5 / sencillo $3 / antiespías $7* (category "Vidrios Templados") and *Hidrogel $4* (category "Hidrogel"), registered in the **Local Vidrios** with 10 test units each (an `ENTRADA` with motivo "Stock de prueba (Local Vidrios)"; replace with real counts). Prices live on the shared catalog, so they apply to every local.
- **Servicio Técnico starter data** (`0019`, idempotent): per phone model *Pantalla 3/4 $25 / Mica $3 / Batería $12* (category "Repuestos") with 10 test units in the Local Servicio Técnico, plus 6 demo `ordenes_servicio` (`registrado_nombre = 'Datos de ejemplo'`, fictitious customers, several states; parts used are real `SALIDA` movements). All placeholder data — replace/ignore later.
- **Test stock**: migration `0010` gives every product with `stock_actual = 0` a random 3–25 `ENTRADA` (motivo "Stock de prueba (aleatorio)"), through the normal movement/trigger path. It is demo data — replace with real counts via "Registrar entrada" or CSV import before real use.

### Multi-local (3 independent stores)

`locales` (migration `0016`; LocalStorage: `db.locales`) holds Local Accesorios, Local Vidrios and Local Servicio Técnico with fixed ids (`lib/constantes-locales.ts`). The **catalog is shared** (products, models, compatibilities, photos, prices, exchange rate); what is per-local is **stock and minimum stock**: table `inventario_local(local_id, producto_id, stock_actual, stock_minimo)` (LocalStorage: `db.inventario`). A local "handles" a product when it has a row there (created by the first `ENTRADA`, by creating/importing the product while that local is active, or by `fijarMinimosLote`). `productos.stock_actual` is kept (by the trigger) as the **total across locales**. `movimientos_inventario`, `ventas` and `devoluciones` carry `local_id`; the stock trigger moves the stock of the movement's local.

- **Context / scope**: `inventoryService.obtenerContextoLocal()` (memoized per page load) resolves session + locales + active scope and publishes `$contextoLocal` (`stores/local.ts`). The administrator picks `'todos'` or one local in the header (`LocalSwitcher.astro`; remembered in `easystem:local-activo`; changing it **reloads the page**); every other role is pinned to their `local_id` (a null one shows a banner and sees nothing). `ContextoLocal.astro` (in `DashboardLayout`) is the provider. Reads (`listarProductos`, `listarMovimientos`, `listarVentas`, `listarDevoluciones`, `listarProductosStockBajo`, `listarOrdenesServicio`) are filtered by the scope automatically; writes use `exigirLocal()` and fail with an actionable message in the "Todos" view (the POS, entries and imports show that notice instead). Options: `listarProductos({ catalogoCompleto: true })` = whole catalog with 0 where the local has none (entries, importer, barcode-duplicate checks, reports lookups); `{ localId }` = project to a specific local (returns/exchanges use the sale's local).
- In "Todos" a product shows the total stock plus a per-local breakdown (`stock_por_local`); its `stock_minimo` is 0 there on purpose: reorder alerts are per local (`vw_productos_stock_bajo` has `local_id`/`local_nombre`, `security_invoker`).
- **RLS (0016)**: administrador = everything; others only rows of their `local_id` (`public.local_actual()`). `SALIDA` movements: any role in their local; `ENTRADA`: administrador (any local) and encargado (own local). Catalog writes (create/edit/import products) stay administrador-only. Encargado sees all sales of their local; vendedor/técnico only their own.
- **Existing data → Local Accesorios** (both the migration and the LocalStorage upgrade `migrarAMultilocal`); fresh LocalStorage demos seed vidrios → Vidrios, "Repuestos" → Servicio Técnico, the rest → Accesorios.
- **Migration order matters**: `0015` (adds the enum values) must run ALONE and finish before `0016` (Postgres can't use a new enum value in the same transaction). The offline queues default a missing `local_id` to Accesorios.

### Servicio técnico (órdenes de servicio)

`pages/servicio-tecnico.astro` + `components/servicio/{NuevaOrden,DetalleOrden}.astro`; table `ordenes_servicio` (0016; LocalStorage: `db.ordenes`); only in locales of type `servicio_tecnico` (a trigger enforces it; the nav link appears only there, or for the administrator in "Todos"). An order has the customer, the device (brand, model, IMEI), what came with it, the reported fault, diagnosis, technician, labor cost and a state Pendiente → En reparación → Listo → Entregado (`Entregado` is final: no more edits; timestamps are set by a trigger / by the service in LocalStorage). **Parts consumed**: `agregarRepuestoOrden` does a `SALIDA` movement ("Repuesto, orden de servicio #N") on the order's local and snapshots the part (price at that moment) in `orden.repuestos`; removing one (`quitarRepuestoOrden`) is an `ENTRADA`, so administrador/encargado only. `total_usd` = parts + labor (shown in $ and Bs.). Charging for the repair is not modeled yet.

### Exchange rate (USD → Bs)

Catalog prices are **in dollars** (`$`); bolívares are never stored on products — they are computed on screen as `precio × tasa del día` (`convertirABs`, `formatearBolivares` "Bs. 1.234,56", `htmlPrecioDual` in `utils/format.ts`).

- The rate is entered **manually** and kept as an append-only history in `tasas_cambio` (migration `0012`; LocalStorage: `db.tasas`); the current rate is the latest row. Any authenticated user may register it (so nobody waits on the admin). `inventoryService.obtenerTasaVigente()` returns `{ hoy, ultima }`, where "today" is the *local* date (`fechaLocalISO`). Offline, a registered rate is queued in `easystem:cola-tasas` and the last one is cached in `easystem:cache:tasa`.
- `components/layout/TasaDelDia.astro` (included by `DashboardLayout`) blocks the first entry of each day with a non-closable dialog until a rate is saved (shows the previous one to confirm; a change >25% asks for a second confirmation). The header chip (`$1 = Bs. …`) reopens it in editable/cancelable mode via the `easystem:abrir-tasa` event. If the rate can't be fetched (e.g. migration not applied) the app is **not** blocked.
- `stores/tasa.ts` (`tasaActual`, a nanostore) is the single source for rendering: pages call `tasaActual.get()` when rendering and re-render with `tasaActual.listen(...)`. It starts from the cached rate so Bs. appear without waiting for the network. Shown in Productos, POS, Dashboard (search + inventory value) and the model→products dialog; Reportes stays in USD.
- POS: a Bs payment method is entered in bolívares (converted at the day's rate), USD cash / Binance USDT in $. `registrarVenta` requires `tasa_cambio` and stores it with the sale.

### Precio de venta fijo en bolívares (migración `0019`)

Un producto puede tener su precio **en dólares** (como siempre: en pantalla se ve en Bs con la tasa del día) o **fijo en bolívares**: p. ej. los vidrios que el cliente vende a Bs 1100 y cuyo precio cambia a mano cada semana o quincena, sin seguir al BCV. Columnas `productos.moneda_precio` ('USD' por defecto | 'BS') y `productos.precio_bs`. **Todo lo demás (POS, ventas, reportes, autorizaciones, nómina) sigue trabajando con `precio_venta` en dólares**: para un producto en Bs `precio_venta` es solo el equivalente de hoy (`usdDesdeBs(precio_bs, tasa)` = `precio_bs / tasa` con **6 decimales**, `utils/precioBs.ts`, para que al reconvertir con la misma tasa salgan los Bs exactos). Ese equivalente se recalcula **dentro del mismo batch que registra una tasa nueva** (`registrarTasa` en `servicios/tasas.ts`: `UPDATE productos SET precio_venta = round(precio_bs / ?, 6) WHERE moneda_precio = 'BS'` + sube la versión de `productos`; demo: `registrarTasa` de `inventoryService`). Sin ninguna tasa registrada no se puede fijar un precio en Bs (409 `sin_tasa`).

- **Dónde se elige**: selector **$ / Bs** junto al precio de venta en «Crear varios productos» (Alta rápida; el marcador por línea también acepta `Bs1100`; el precio de la lista toma la moneda elegida) y en el formulario de producto. Un producto **por cantidad** (< $3) SÍ puede tener precio fijo en Bs (los vidrios de $1,22 a Bs 1100): el tope de $3 se revisa sobre el equivalente en dólares de la tasa de hoy. Lo ven y usan administrador, gerente y encargado (el catálogo es compartido). `resolverPrecio` (`servicios/catalogo.ts`) decide lo que se guarda y revisa el tope de $3 sobre el equivalente en dólares.
- **Editar**: `actualizarProducto` con `moneda_precio`/`precio_bs` cambia de moneda; un `precio_venta` suelto sobre un producto que está en Bs se **ignora** (protege contra pantallas viejas y el **importador CSV, que no cambia el precio de los productos en Bs**: usar «Cambiar precios»).
- **Cambiar precios en lote** (Productos → «Cambiar precios», administrador, gerente y encargado; `POST /api/productos/precios-lote` `{ ids, moneda, precio }`, `cambiarPreciosLote` en `servicios/catalogo.ts` + `inventoryService.cambiarPreciosLote`, demo con la misma lógica): pone el MISMO precio ($ o Bs fijo) a los productos de la lista que se ve (categoría + búsqueda) o solo a los marcados con «Seleccionar» (hasta 3000, en UN batch atómico con `sentenciasCambio`, trozos de 90 ids por sentencia por el límite de parámetros de D1). Es la forma de cambiar de una vez, por ejemplo, todos los vidrios de Bs 1100 a Bs 1250, o de pasar los que estaban en $1,22 a Bs 1100. Un producto por cantidad que quedaría en $3 o más rechaza TODO el lote (409 `precio_no_permitido`).
- **POS exacto en Bs**: el total en dólares se redondea a centavos y con una tasa alta un centavo son varios Bs (Bs 1100 saldrían como 1.098). Por eso el carrito, el cobro y «Completar» usan los Bs EXACTOS de las líneas con precio fijo en Bs (`bsExactoDeLinea` / `totalBsExactoDelCarrito` en `ventas.astro`, `htmlPrecioDual(..., bsExacto)`, `FormularioPagos.establecerTotal(usd, totalBs)`); una línea con precio de promotor/descuento (que va en dólares) o la instalación se convierten con la tasa como antes. Límite: «Completar» propone el Bs exacto solo cuando lo que falta es el total completo (pago único); en pagos divididos propone `falta × tasa`. La venta se guarda en dólares como siempre (el redondeo en Bs de hasta $5 ya se acepta).

### Split payments

A customer can pay one sale with several payment types (migration `0013`). The POS dialog has one row per payment (type + amount in that type's currency: Bs. for `BS_*`, $ for the rest; no repeated types; "Completar" fills what's left; the sum must equal the total ±$0.01, unless "¿Se debe dar vuelto?" = Sí). `DatosVenta.pagos: PagoVenta[]` = `{ metodo, monto_usd, monto_bs }`; the sale stores them in `ventas.pagos` (jsonb) and `ventas.metodo_pago` is the single type or `'MIXTO'`; `total_bs` = sum of what was received in Bs. **Always read payments through `pagosDeVenta()` (`utils/pagos.ts`)** — sales saved before 0013 have no `pagos` and get one synthetic payment. `resumirPorMetodo` (history summary + Reportes) groups by payment line, not by sale: a mixed sale adds each part to its own type. If only some lines of a sale were committed, the payments are scaled proportionally (`ajustarPagos`).

### Nombre y apellido en un solo campo (POS)

En el cobro del POS el cliente y los dos formularios de promotor (precio de promotor y promotor que instala) piden **«Nombre y apellido» en UN solo campo escrito corrido**. `separarNombreCompleto` / `unirNombre` (`utils/promotor.ts`) lo parten en las dos piezas que sigue guardando el sistema (1 palabra = solo nombre; 2 = nombre y apellido; 3 = el primero y el resto; 4+ = mitad y mitad): el modelo de datos, la API y el servidor no cambian y el nombre completo siempre se ve igual que se escribió. Al cliente se le sigue exigiendo nombre Y apellido (al menos dos palabras); al promotor, lo que ya se pedía. El autocompletado por cédula une las dos piezas en el campo. `FormularioPromotor` (Pendientes → «+ Agregar promotor») conserva sus dos campos. Test: `tests/cliente/nombre-completo.test.ts`.

### Redondeo en bolívares (el cliente paga de más)

Con un pago en Bs (p. ej. pago móvil) la gente suele redondear el monto. Si lo recibido SUPERA el total y no se eligió dar vuelto, en vez del error rojo «Los pagos se pasan por…» el cobro se acepta como **redondeo** cuando hay un pago en Bs y el exceso es ≤ `REDONDEO_MAXIMO_USD` ($5; evita que un error de tecleo pase como redondeo). `absorberExcesoEnBs` (`utils/pagos.ts`, pura) descuenta el exceso del ÚLTIMO pago en Bs: `monto_bs` queda con lo que de verdad entregó, `monto_usd` con lo que cuenta para el total (Σ `monto_usd` = total, la invariante de siempre) y el nuevo campo opcional `PagoVenta.monto_bs_debido` con los Bs que DEBÍA pagar (`monto_usd × tasa`); `bsDeMas()` = la diferencia. `FormularioPagos` lo avisa en ámbar («Pagó Bs X y debía Bs Y… la venta se registra igual») y `leer()` lo devuelve ya ajustado. Va dentro del JSON `ventas.pagos` (sin migración). `total_bs` y el **cuadre de caja** usan `monto_bs`, o sea lo que realmente entró a la caja. Validación en `redondeoValido` (cliente `registrarVenta` y servidor `guardarVenta`, 400 `datos_invalidos`: solo tipos en Bs, debido < pagado, exceso dentro del tope). «Ventas realizadas» muestra «Redondeo: el cliente pagó Bs X y debía pagar Bs Y (Bs Z de más)» (y en el CSV `[debía Bs…]`). Si solo se alcanzó a registrar parte de la venta (`ajustarPagos`) el aviso de redondeo se descarta. Con «¿Se debe dar vuelto?» = Sí todo sigue como antes. Tests: `tests/cliente/redondeo-pagos.test.ts`, `tests/server/redondeo-pago-bs.test.ts`.

### Change (vuelto)

The payments form lives in `utils/formularioPagos.ts` (`FormularioPagos`, mounted on an empty container; used by the POS and by the exchange dialog). With "¿Se debe dar vuelto?" = Sí the received amounts may exceed the total; the excess is the **vuelto**, given in one of `METODOS_VUELTO` (USD cash, Bs cash, pago móvil) and stored in `ventas.vuelto` (migration `0014`). Invariant: `Σ pagos.monto_usd − vuelto.monto_usd = total`. `total_bs` is net (Bs received − Bs vuelto). `resumirPorMetodo` subtracts the vuelto from the method it was handed out with (net cash view).

### Returns and exchanges (devoluciones)

From **Ventas realizadas**, an **administrator or encargado (of that local)** can open "Devolución / cambio" on a sale (`components/ventas/DevolucionVenta.astro`, events `easystem:abrir-devolucion` / `easystem:ventas-cambiaron`). `inventoryService.registrarDevolucion`: validates quantities against what was sold minus earlier returns; first moves stock OUT for replacement items (best-effort reverse if one fails), then stock IN (`ENTRADA`) for the returned ones, then saves a row in `devoluciones` (migration `0014`; LocalStorage: `db.devoluciones`). `diferencia = total_nuevo − total_devuelto`: > 0 the customer pays it (`pagos`/`vuelto`, same form), < 0 it is refunded with one of `METODOS_REEMBOLSO` (Bs amount at *today's* rate), ≈ 0 nothing. Restricted to administrador/encargado because returned stock is an `ENTRADA` and money moves; the stock goes back to the *sale's* local (`venta.local_id`), not the active one. A vendedor can *read* the returns of sales they can see. Needs connection (not queued). Records are immutable (no update/delete). Reportes subtracts returned lines from revenue, cost and unit rankings (replacement items are already counted as `SALIDA`); the history shows net totals.

### Sales record (customer + payment type)

The POS asks for cédula (`V-`/`E-` + 5–9 digits), nombre, apellido, teléfono and *tipo de cobro* (`utils/pagos.ts`: Bs pago móvil / Bs punto de venta / Bs efectivo / USD efectivo / Binance USDT; `esMetodoBolivares` = the `BS_*` ones) in the same dialog that confirms the sale. `inventoryService.registrarVenta(items, { cliente, metodo_pago })` first moves stock (one `SALIDA` per line, motivo "Venta POS") and then saves a row in `ventas` (migration `0011`; LocalStorage: `db.ventas`) with the folio, customer, total (USD), `tasa_cambio`, `total_bs` (only when the payment is in Bs: total × rate, rounded to cents, frozen at sale time) and an `items` snapshot (name/code/price at sale time). The folio is assigned by the database (identity), so it persists across sessions.

Tests: `codigo-manual.test.ts` y una fila en `matriz-roles.test.ts`.
- **Reportes** adds "Ventas por tipo de cobro" (chart + table + printable section) from the same `listarVentas`. It only covers sales saved in `ventas` (i.e. since migration 0011); the stock-movement-based revenue/cost figures are unchanged.

### SaaS subscriptions and role hierarchy

EASYSTEM is sold as a service: **one subscription per local** (migrations `0020`–`0023`). Edward is the only client for now — there is **no multi-company isolation** (a second client would need a `tenant_id` on everything; note it before onboarding one).

- **Hierarchy** (`Rol` in `auth.ts`; enum `rol_usuario`): **administrador** (the developer/SaaS owner: full access, never blocked by a subscription) > **gerente** (the client's owner: access to ALL locales, catalog, entries, devoluciones, reports) > **encargado** (one local) > **vendedor** / **tecnico** (one local). Helpers: `esAdministrador` (strict), `esGlobal` (administrador + gerente = all locales/catalog), `esGerencia` (+ encargado), `rolesAsignables(actor)` (administrador → all six; gerente → encargado + vendedor + tecnico + contador), `puedeGestionarUsuario(actor, objetivo)`. SQL mirrors: `es_administrador()`, `es_global()`. Anything that used to say `rol === 'administrador'` for business operations (catalog, entries, importer, switcher) now uses `esGlobal`.
- **Users module** (`/usuarios`, administrador + gerente): the administrador creates/edits/deletes anyone (not himself); the gerente only creates, edits (local, estado, password) and **deletes** encargados, vendedores, técnicos and contadores, and never sees administradores. Deleting = RPC `eliminar_usuario` (deletes the auth account; sales/orders keep their snapshot name, the FK goes null) — the static site cannot call the Auth admin API, so it's SQL. Nobody changes their own role/estado (trigger `proteger_perfil`).
- **Edit dialog + passwords** (`/usuarios`, "Editar" button; administrador + gerente): changes **nombre, correo**, rol, local and/or password in one dialog (a user edits only his own nombre, correo and password: rol/local are hidden for himself). Nombre y correo viajan con rol/local en UN solo `PATCH /api/usuarios/:id` (`actualizarUsuario` en `servicios/usuarios.ts`: actualiza `perfiles` Y la tabla `user` de Better-Auth en un batch; el correo se guarda en minúsculas, es el de inicio de sesión, y uno repetido da 409 `correo_repetido` sin cambiar nada; mismos permisos de jerarquía que rol/local, salvo que cada quien puede editar el suyo; no cierra sesiones; las ventas/órdenes ya hechas conservan el nombre anterior como copia). Tests: `usuarios.test.ts` (bloque «nombre y correo»), `auth.test.ts`. Password = RPC `cambiar_clave_usuario` (migration `0024`; bcrypt via `extensions.crypt`; administrador any user, gerente encargado/vendedor/tecnico + himself; it also deletes the target's sessions). **Existing passwords can never be shown**: Supabase only stores a bcrypt hash and we must not keep plaintext. The dialog lets you see what you type (Ver/Ocultar), generate one, and shows the saved password once (with Copiar). Rol/local are grouped lists, not inline selects any more. In LocalStorage mode the demo passwords are plaintext (`easystem:usuarios`) but the UI behaves the same.
- **Modelos de teléfono is hidden from the encargado and vendedor of the Local de controles** (`ocultoEnLocal` in `navLinks.ts`, decided by the pure `enlaceVisible(enlace, rol, tipoLocal, vistaTodos)`; the Sidebar uses it and `/modelos` sends them to `/` if they type the URL). UI-level only, like the vendedor's missing Movimientos; administrador/gerente still see it in every local.
- **Historial = Ventas realizadas + Movimientos**: ONE sidebar link "Historial" (`/historial-ventas`, `tambienActivoEn: ['/movimientos']` keeps it highlighted on both pages) with two tabs (`components/layout/PestanasHistorial.astro`, shown only to administrador/gerente/encargado). Each tab is still its own page with its own filters and loading (so no id collisions and each keeps its state); switching reloads the page. The técnico, who can't see sales, keeps a plain "Movimientos" link and no tab bar. Vendedor sees neither.
- **Menus**: encargado/vendedor/tecnico never get Usuarios; the **vendedor** also doesn't get *Ventas realizadas* nor *Movimientos* (nav + page `roles` + the dashboard "Movimientos recientes" widget). This is UI-level only: the DB still lets a vendedor read his own sales and the local's movements, because the POS needs them (insert + read-back).
- **Página principal** (what used to be called "Dashboard": the user-facing name everywhere is now "Página principal" — sidebar `navLinks.ts` and page title; the code keeps `DashboardLayout`/`components/dashboard/`) **summary cards** (Total de productos, Valor del inventario, Alertas de stock bajo; `#dash-resumen` in `pages/index.astro`). "Total de productos" cuenta ítems del catálogo del alcance activo y lleva al lado las **unidades físicas en stock** (Σ `stock_actual`, `#stat-total-unidades`; `StatCard` acepta `secundario`) are for **administrador and gerente only** (`esGlobal`); the encargado, vendedor and técnico never see them (the section is `hidden` by default and the script reveals it). UI-level only. The low-stock table, quick search and recent movements stay as before.
- **Subscription data**: `locales.subscription_status` ('ACTIVE'|'SUSPENDED'|'PAST_DUE') + `subscription_expires_at` (optional: past it, an ACTIVE local counts as blocked); `perfiles.status` ('active'|'inactive') + `perfiles.last_force_logout_at`; audit table `suscripcion_eventos` (administrador reads it). Only the administrador can write `locales` / use the RPCs below.
- **Enforcement is in the database (RLS), not the UI**: helpers `usuario_habilitado()` (active profile AND JWT `iat` ≥ `last_force_logout_at`), `local_vigente(id)`, `local_accesible(local_id)` (administrador: always; gerente: any local that is vigente; others: own local if vigente) and `catalogo_accesible()`. Every business-table policy (catalog, tasas, inventario_local, movimientos, ventas, devoluciones, ordenes_servicio, product photos) uses them: a suspended/past-due/expired local, an inactive user or a force-logged-out token get **empty reads and rejected writes**. If **all** locales are blocked the gerente is blocked too; the administrador never is. Don't add business-table policies without `local_accesible`/`catalogo_accesible`.
- **RPCs** (SECURITY DEFINER; administrador only unless noted): `estado_cuenta()` (any authenticated user: `{acceso, motivo, local_nombre, subscription_status, ...}`, motivo ∈ ok|local_suspendido|usuario_inactivo|sesion_cerrada|sin_perfil), `cambiar_suscripcion_local(local, estado, vence, cambiar_vencimiento)`, `usuarios_sistema()`, `cerrar_sesion_forzada(usuario)` (sets `last_force_logout_at`, deletes `auth.sessions`/`refresh_tokens`; the old access token stops working at once because policies compare its `iat`), `cerrar_sesiones_local(local)`, and `eliminar_usuario(usuario)` (administrador any, gerente only encargado/vendedor/tecnico). No `supabase.auth.admin.*` on purpose: it needs the service-role key, which a static site must never hold.
- **Client guard = the "middleware"** (static site, no SSR): `auth.ts` → `protegerPagina` calls `obtenerEstadoCuenta()` (RPC `estado_cuenta`) on every page load and then every 60 s / on `online` / when the tab becomes visible (`iniciarVigilanciaCuenta`). Blocked → `local_suspendido`: `/subscription-suspended` (standalone page, retry + logout buttons, auto-enters when reactivated); `usuario_inactivo`/`sesion_cerrada`: sign out and `/login?motivo=...` (login shows the message). **It fails open** when the RPC errors (offline POS, or 0021/0023 not applied yet) — the DB is the real gate. The local switcher shows suspended locales as "(suspendido)"; for the gerente they are disabled, the administrador can still enter them.
- **Panel** `pages/admin/subscriptions.astro` (administrador only, nav "Suscripciones"): a card per local (Activar / Suspender / En mora, expiry date, "cerrar las sesiones de este local") and the users table with "Cerrar sesión forzada". Functions in `auth.ts`: `listarSuscripciones`, `cambiarSuscripcionLocal`, `listarUsuariosSistema`, `cerrarSesionForzada`, `cerrarSesionesLocal`.
- **LocalStorage parity** (same rules): subscriptions in `easystem:suscripciones` (merged into `listarLocales()`), forced logouts in `easystem:cierres-forzados` (compared with the session's `emitida_en`), user status in `easystem:usuarios`; demo gerente `gerente@edwardaccesorios.com` / `gerente123`. `obtenerEstadoCuenta` simulates `estado_cuenta()`.
- **Migrations**: `0020` (enum `super_admin`, superseded: harmless leftover; `0023` turns any such profile into administrador), `0021` (subscriptions), `0022` (enum `gerente`, run ALONE), `0023` (hierarchy; rewrites the policies/RPCs for administrador/gerente and drops `es_super_admin()`). Run in order `0019`→`0020`→`0021`→`0022`→`0023`→`0024` (`0024` = password change RPC)→`0025` (encargado catalog + stock lock)→`0026` (enum contador, ALONE)→`0027` (payroll)→… →`0032` (independent workers)→`0033` (unit codes)→`0034` (cuadre de caja). After them, if the client's owner account is still `administrador`: `update public.perfiles set rol = 'gerente' where email = '...'`.

### Ingreso de mercancía and barcode labels

`pages/ingreso.astro` (nav "Ingreso de mercancía"; administrador, gerente, encargado) is THE place to receive stock, create new products and print labels. It replaced the "Registrar entrada" and "+ Nuevo producto" buttons of Productos (the old `EntradaStock` dialog is gone; Productos now has a link "Ingresar mercancía" and a "+ Stock" link per row → `/ingreso?producto=<id>`). Productos keeps browsing, **Editar** and the CSV importer (administrador/gerente only).

- **Flow**: a *lote* (list of lines) — add by search or camera scan (`data-abrir-escaner` / `easystem:codigo-escaneado`; scanning a known product again = +1 unit; an unknown code offers "+ Nuevo producto" with the code prefilled) → each line has *Ingresan* (units, 0 = labels only) and *Etiquetas* (follows the units until edited by hand) → **Registrar ingreso** does one `registrarMovimiento` ENTRADA per line (motivo = campo opcional **Proveedor**: con texto queda «Compra a proveedor: X», vacío «Ingreso de mercancía»; `utils/proveedor.ts` `motivoDeIngreso`, sin tabla de proveedores; needs a concrete local, not "Todos"; sequential, lines that fail stay in the lote; registered lines keep their label count) → **Imprimir etiquetas**. The lote is remembered per user in localStorage (`easystem:ingreso-lote:<userId>`), the label size in `easystem:formato-etiqueta`.
- **New product** = the existing `FormularioProducto` dialog opened with `easystem:abrir-producto` `{ sinStock: true, codigo? }` (no initial stock: the lote registers the entry); it also emits `easystem:producto-guardado` `{ productoId, nuevo }`, which the page uses to drop the new product into the lote. Don't build a second product form.
- **Encargado creates AND edits products** (migration `0025`, policies use `es_gerencia()` = administrador/gerente/encargado); deleting products stays administrador/gerente. The catalog is shared, so an encargado's edit shows in every local. The **purchase price is hidden from the encargado** (form field hidden; on edit `precio_compra` isn't sent; new products get 0). The CSV importer remains administrador/gerente. `0025` also lets the encargado upsert `inventario_local` rows of his own local and **locks stock**: `authenticated` can only write `inventario_local.stock_minimo` (column grants), so stock only changes through movements — never send `stock_actual` to that table (`asegurarEnLocal` no longer does).
- **Labels carry a QR code by default** (`utils/qr.ts`, library `qrcode-generator`, level M, content = the product code, so every scanner yields the same value): phone cameras and 2D readers read it; classic LASER scanners can't, so the Ingreso panel has a "Tipo de código" switch (QR / Barras, remembered in `easystem:etiqueta-tipo-codigo`). QR layout = code on the left, name + number on the right (`qrMm` per format). If a QR can't be built it falls back to bars.
- **Etiqueta con QR en dos mitades**: a la izquierda el QR y debajo la palabra fija **EGC** (`TEXTO_BAJO_QR` en `etiquetas.ts`), a la derecha el nombre del producto y debajo su código numerado (INF000001); sin logo (se probó un logo abajo y el dueño prefirió esto). Lo dibujan igual `svgEtiqueta` (PNG/PDF/tira, `etiquetaImagen.ts`: el QR cede lo justo para que quepan él y el EGC, nombre hasta 4 renglones) y `htmlEtiqueta` (vista previa e impresión directa: `.etq-izq` con `.etq-qr` + `.etq-bajo-qr`, y `.etq-texto`). Las etiquetas de **barras** no llevan EGC. Tests en `etiquetaImagen.test.ts`.
- **Bars**: `utils/codigoBarras.ts` (no dependencies; EAN-13, UPC-A as EAN-13, EAN-8, otherwise Code 128-B; verified bit-for-bit against JsBarcode) draws the SVG; `utils/etiquetas.ts` has the formats (roll 50×30, roll 40×25, A4 sheet 3×8 of 70×37 mm — no printer chosen yet, add formats there), the label HTML (barcode + number + product name) and `imprimirEtiquetas()` (temporary `#etiquetas-impresion` container + dynamic `@page` + `window.print()`, hides the rest of the page). Internal codes are EAN-13 (`utils/codigos.ts`) so any scanner reads them; a code the font can't draw (non-ASCII) prints a warning label instead of bars.
- **Cuándo una unidad cuenta como "impresa"** (`impresa_en`, lo que el POS avisa como "Aún sin etiqueta impresa" y lo que listaba el botón «Agregar todo lo que está sin etiqueta», ya QUITADO de Ingreso a pedido del dueño; para reimprimir quedan «Reimprimir etiquetas» y escanear/buscar cada producto): al **Descargar** el PDF/imágenes de la ventana de etiquetas y también con **Listo**, pero una sola vez por ventana (`anotarImpresas` en `ingreso.astro`; una reimpresión no se suma dos veces). **Tras "Listo" el lote se vacía solo** cuando todo salió bien (no es reimpresión, las etiquetas quedaron anotadas, entraron todas en la tira y ninguna línea tiene unidades por ingresar): avisa "Marcadas N etiquetas como impresas. El lote quedó vacío.", deja visible ese aviso y "Reimprimir estas" (que usa su propia copia de las etiquetas, no el lote). Si quedó algo pendiente (sin red, unidades sin registrar, más etiquetas que el tope por PDF) el lote se conserva. Antes solo se anotaba con "Listo": quien descargaba, imprimía desde la app de la impresora y cerraba con "Cerrar" dejaba etiquetas ya pegadas como "sin etiqueta". Las unidades que ya estaban así en producción se corrigen una vez con SQL (`UPDATE unidades_producto SET impresa_en = … WHERE impresa_en IS NULL AND estado = 'DISPONIBLE'`), no con migración: es una afirmación del dueño ("todo ya tiene etiqueta").
- **Alta rápida ("Crear varios productos")**: botón del Ingreso (pensado para el teléfono: la ventana `components/ingreso/AltaRapida.astro` ocupa toda la pantalla). Se pone UNA vez la categoría, el prefijo, la cantidad y el precio de venta (y el de compra, solo administrador/gerente) y se escribe UN PRODUCTO POR LÍNEA; al final de una línea puede ir `x3` (unidades) y/o `$12` (su precio). Lo lee `utils/altaRapida.ts` (`parsearAltaRapida`, puro: suma los nombres repetidos, avisa de líneas malas; máx. 100). La vista previa marca cada línea Nuevo / "Ya existe: se suma al lote" (por nombre normalizado contra TODO el catálogo: lo que ya existe no se duplica, solo entra al lote). Crea con `inventoryService.crearProductosRapidos` → `POST /api/productos/rapido` (`crearProductosRapidos` en `servicios/catalogo.ts`: administrador/gerente/encargado, el servidor genera el EAN-13 interno y la referencia `CTL-001`, stock mínimo 0, todo o nada; al encargado el precio de compra se le fuerza a 0) y después `asegurarEnLocal`. Avisa con `easystem:alta-rapida-creada` `{ items: [{ productoId, cantidad }], nuevos }` y el Ingreso los mete al lote (cantidad = etiquetas). Recuerda lo escrito en `easystem:alta-rapida` (si falla, el texto no se pierde). **Cámara de ráfaga** (`components/ingreso/RafagaFotos.astro`): el botón "Crear y tomar fotos" crea los productos NUEVOS y abre, con el evento `easystem:abrir-rafaga` `{ productos: [{ id, nombre }] }`, una cámara a pantalla completa (`getUserMedia`, un solo permiso) que fotografía la lista de corrido: el obturador toma la foto del producto de arriba y pasa al siguiente, "Saltar" lo deja sin foto, "Repetir" vuelve al anterior, "Terminar" lleva al resumen (qué quedó sin foto y el estado de las subidas). Las fotos se reducen (720 px, WebP) y se suben EN SEGUNDO PLANO con `inventoryService.guardarImagenProducto` (cola: 2 a la vez, nunca dos del mismo producto juntas, 3 intentos con espera, "Reintentar las que fallaron" en el resumen); `beforeunload` avisa si hay subidas pendientes (la cola vive en memoria: cerrar la pestaña las pierde). Si el navegador no abre la cámara (sin permiso o sin `getUserMedia`) el obturador abre la cámara normal del teléfono (`<input capture>`), una foto por toque con el mismo flujo. Avisa con `easystem:rafaga-fotos` (Ingreso refresca el catálogo). No hay "usar la foto de otro producto" a propósito (lo pidió así el dueño). **Un solo permiso de cámara**: el iPhone vuelve a pedir permiso cada vez que se abre `getUserMedia` de nuevo, así que al cerrar la ventana la cámara se deja *aparcada* (pistas con `enabled = false`, sin mostrarse) 10 minutos y la siguiente ráfaga la reutiliza sin preguntar (`detenerCamara` / `flujoAparcado` en `RafagaFotos.astro`; se suelta en `pagehide`). El escáner de códigos (`CamaraEscaner`, html5-qrcode) maneja su propia cámara y no comparte esto. Si aun así pregunta siempre: Ajustes del iPhone → Safari → Cámara → Permitir para el sitio.
- **Campos de precio con coma**: el teclado del teléfono en español escribe la coma y un `<input type="number">` la descarta; los precios del formulario de producto, del alta rápida y de «Cambiar precios» son texto y se leen con `leerPrecioEscrito` (`utils/precioBs.ts`: coma o punto decimal, hasta 2 decimales; en Bs «1.100» = 1100). Tests: `altaRapida.test.ts`, `alta-rapida.test.ts`, fila en `matriz-roles`.
- **Tope de etiquetas por ventana**: el PDF (modo recomendado, una página por etiqueta) admite hasta `MAX_ETIQUETAS_POR_PDF` = 1000 etiquetas por vez (`etiquetaImagen.ts`; con más avisa «faltan N» y se vuelve a pulsar Imprimir). La **tira** (una sola imagen: límite del lienzo del navegador) y las **imágenes sueltas** (y la vista previa) siguen en `MAX_ETIQUETAS_POR_TIRA` = 40: con más de 40 esas dos opciones se desactivan y solo queda el PDF.
- **Registrar todo el lote de una vez y de una vez imprimir**: `inventoryService.registrarIngresoLote` manda todas las líneas en tandas (`utils/tandas.ts`: ≤50 movimientos y ≤500 unidades) a `POST /api/movimientos/lote` (atómico por tanda) en vez de una petición por producto. Si el servidor rechaza una tanda (4xx) reintenta línea por línea para que solo falle la que tiene el problema (queda en el lote); con error de red/5xx NO reintenta a ciegas (podría ingresar dos veces): marca las líneas como "no se pudo confirmar, revisa el stock". Botones del pie: **Registrar e imprimir etiquetas** (principal: registra y, si no hubo fallos, abre directo el diálogo de etiquetas; sin nada que ingresar solo imprime), **Solo registrar ingreso** e **Imprimir etiquetas**. Sin impresión directa (ESC/POS/WebUSB): se descarga el PDF y se abre desde la app de la impresora.
- **Lote vacío = sin zona de registrar**: mientras el lote no tenga productos, el pie del lote (motivo del ingreso, resumen, "Imprimir etiquetas" y "Registrar ingreso") no se muestra (`#ig-pie[data-vacio="true"]` en el CSS de `ingreso.astro`, marcado por `pintarLote()`); solo quedan visibles los avisos que haya (éxito, error o "Reimprimir estas"). El diálogo de etiquetas ya NO tiene el botón "Compartir con WePrint": se descarga el PDF/las imágenes y se abren desde la app de la impresora (el compartir del ticket del POS no cambia).
- **Label size is chosen AT PRINT TIME**: the "Imprimir/Reimprimir etiquetas" dialog (`ig-galeria`) has its own "Tamaño de la etiqueta" (fixed formats, incl. `rollo-40x30`, or "Otra medida" with ancho × alto in mm, 20–120 × 12–100). It mirrors the same state as the side panel (`ig-formato`/`ig-ancho`/`ig-alto`, remembered in `easystem:formato-etiqueta` / `easystem:formato-personalizado`); changing it regenerates the PDF, strip and images, and the files are named with the size (`etiquetas-40x30mm.pdf`; each PDF page = exactly one label of that size).

### Mercancía: Ingreso + Descargo (traslados entre locales y bajas)

`pages/ingreso.astro` (URL `/ingreso`, nav "Mercancía"; administrador, gerente, encargado) now has two tabs like Nómina: **Ingreso** (everything described above) and **Descargo** (`components/mercancia/Descargo.astro`, deep link `/ingreso#descargo`; the tab switch dispatches `easystem:mercancia-pestana`, and each panel ignores `easystem:codigo-escaneado` while it is hidden). Migration `0006`; server in `src/server/servicios/traslados.ts`; client in `lib/db/traslados.ts` + `inventoryService` (`listarDestinosTraslado`, `listarTraslados`, `despacharTraslado`, `recibirTraslado`, `cerrarTraslado`, `darDeBaja`, `revertirBaja`, with LocalStorage parity in `db.traslados`). Everything needs a connection (not queued).

- **Unit states**: DISPONIBLE · VENDIDA · EN_TRANSITO (left a local, not yet received: counts in no stock, can't be sold anywhere) · BAJA (`baja_motivo` DANADA/USADA/GARANTIA, `baja_nota`, `baja_en`, `baja_por`). Stock of a local still = its DISPONIBLE units. Trigger `trg_unidad_transicion` only allows DISPONIBLE ↔ VENDIDA/EN_TRANSITO/BAJA, so two operations fighting over one piece abort the second whole batch (the unit UPDATEs are intentionally unfiltered).
- **Movement types** (`TipoMovimiento`): ENTRADA, SALIDA, `TRASLADO_SALIDA`, `TRASLADO_ENTRADA`, `BAJA`. Only ENTRADA/SALIDA are sales/purchases (reports count only those); `sumaStock(tipo)` decides the sign, `utils/movimientos.ts` the label/colour/filter ("Traslados y bajas" in Movimientos). `esquemaMovimiento` (manual API) still accepts only ENTRADA/SALIDA (`TipoMovimientoManual`).
- **Traslado in two steps** (`traslados` + `traslado_unidades`, folio from `contadores`): the origin DISPATCHES scanning piece codes (units → EN_TRANSITO, one TRASLADO_SALIDA per product at the origin) and the destination RECEIVES scanning (units → DISPONIBLE with `local_id` = destination, SAME code so the label is not reprinted; TRASLADO_ENTRADA at the destination; partial receipts allowed). **Cerrar** returns what didn't arrive to the origin (TRASLADO_ENTRADA "no llegó") and leaves the traslado RECIBIDO (something arrived) or ANULADO (nothing). Dispatch/baja need the piece DISPONIBLE in the given local; receive only for pieces of that traslado.
- **Permissions** (service re-checks; matrix in `matriz-roles.test.ts`): administrador/gerente/encargado only; an encargado dispatches/bajas only from his own local, receives only at his own, closes if he is origin or destination; `revertirBaja` administrador/gerente. Every call first runs `alcanceDe` (a suspended/blocked local gives 403 before anything leaks). `GET /api/traslados/destinos` lists all vigente locales (an encargado only "sees" his own elsewhere) so he can choose a destination.
- **Bajas** (`POST /api/bajas`): piece leaves the stock (movement BAJA) and keeps its code; "Bajas recientes" lists them with "Revertir" (ENTRADA "Reversión de baja", unit back to DISPONIBLE). `GET /api/unidades?estado=` now accepts EN_TRANSITO and BAJA.
- Realtime: `traslados` is in `TABLAS_LOCAL` (server) and `TABLAS_TIEMPO_REAL` (client).

- **Inventario (third tab, `components/mercancia/Inventario.astro`, deep link `/ingreso#inventario`)**: prints the sheet to count a local by hand and compare with the system. Two sheets, both built by pure functions in `utils/hojasImpresas.ts` (`htmlInventarioPorProducto`: one line per product with the system quantity and blank "Contado"/"Diferencia" columns, subtotal per category; `htmlInventarioPorPieza`: the code of EVERY DISPONIBLE piece with a ☐, grouped by product, plus "sobran"/"faltan" lines). Local picker for administrador/gerente (the encargado is pinned to his own), category filter, "include stock 0" (por producto only). Data is fetched at print time (`listarProductos({ localId })` + `listarUnidades({ estado: 'DISPONIBLE', localId })`), never from the screen's stale copy; EN_TRANSITO and BAJA pieces are not counted. Read-only: it writes nothing.

### Payroll (Nómina) and the contador role

`pages/payroll.astro` (route `/payroll`, nav "Nómina") — personal and pay (fortnightly for fixed staff, daily for independent resellers) for ALL locales. Roles: **administrador, gerente and the new `contador`** (`puedeNomina()`); encargado/vendedor/tecnico get nothing (nav, page `roles`, `exigirAccesoNomina()` in the service, and RLS).

- **Tables** (migration `0027`, Spanish names like the rest of the schema): `empleados` (the people who get a salary — NOT the login accounts in `perfiles`; `local_id`, nombre, apellido, cedula unique, cargo, `salario_base` = MONTHLY salary in USD, `frecuencia_pago` 'QUINCENAL', estado ACTIVO/INACTIVO, fecha_ingreso; never deleted, set INACTIVO) and `nominas` (one row per empleado + período: `pago_base` (= salary/2, snapshot) + `bonos` − `deducciones` = `total_pagado` enforced by a CHECK; estado_pago PENDIENTE/PAGADO, `pagado_en`, notas). `UNIQUE(empleado_id, periodo_inicio, periodo_fin)`. Trigger `preparar_nomina`: `local_id` always comes from the empleado, a PAGADO row can't be changed (and policies stop deleting it); PENDIENTE rows can be adjusted/deleted. All amounts are USD (no Bs. here: the contador can't read the exchange rate).
- **Access**: RLS function `nomina_accesible(local)`: administrador always; gerente and contador when the local's subscription is vigente. `es_contador()` too. The contador sees **no business data** (no ventas/stock/catalog; `es_global`/`es_gerencia`/`local_accesible` exclude it) — it can read `locales` (to filter) and its own profile. `estado_cuenta()` treats the contador like the gerente (blocked only if every local is suspended). The administrador AND the gerente create/edit/delete contadores and reset their password (`rolesAsignables('gerente')` = encargado/vendedor/tecnico/contador; the gerente still can't touch administradores or other gerentes).
- **Client**: `utils/nomina.ts` (pure: `quincenaDe/Anterior/Siguiente` — 1–15 and 16–end of month, dates as "aaaa-mm-dd" text —, `pagoBaseQuincenal`, `totalPago`, `validarAjustes`); data in `inventoryService` (`listarEmpleados`, `crearEmpleado`, `actualizarEmpleado`, `listarNominas`, `guardarPagoQuincenal`, `generarPagosPendientes`, `eliminarPagoPendiente`; Supabase via `lib/db/nomina.ts`, LocalStorage `db.empleados`/`db.nominas` with 6 fictitious demo employees from `empleadosMock()`). Needs a connection (not queued offline).
- **Page**: quincena selector, local filter ("Todos" = consolidated with subtotal per local and a grand total, or one local), search, show inactive, "Generar quincena" (creates PENDIENTE rows for active employees without one), "Imprimir reporte" (`window.print()`, controls hidden), summary cards (active, total, paid, pending), employee dialog and payment dialog (bonos/deducciones/notas; "Guardar pendiente" or "Marcar como pagado" with confirm; paid payments are read-only).
- **Payment proof** (migration `0029`): the pay dialog takes an OPTIONAL screenshot of the payment (`nominas.comprobante_path`). It is shrunk in the browser (`reducirImagen(archivo, { ladoMaximo: 1280 })`, readable text) and goes to the **private** Storage bucket `comprobantes-nomina` (path `<local_id>/<empleado>-<período>-<ts>.jpg`; policies use `comprobante_accesible(name)` = `nomina_accesible` of the first path level, so same access as the payroll: administrador, gerente, contador). Never public: `urlComprobanteNomina()` asks for a 1-hour signed URL each time. Order in `guardarPagoQuincenal`: upload → save the payment (deleting the upload if that fails) → delete the replaced file. A PAGADO payment can't be edited, so the proof must be attached when paying (or while PENDIENTE); once paid it can only be viewed. LocalStorage mode keeps it as a data URL inside the payment (`guardarDBEstricto` reports a full quota).
- **Two kinds of worker** (migration `0032`): `empleados.tipo` = **FIJO** (as above: fortnightly) or **INDEPENDIENTE** (no salary/fortnight; `salario_base` = 0, `frecuencia_pago` = 'DIARIO'; a CHECK keeps tipo and frecuencia coherent). The type is chosen when registering and **can't be changed afterwards**. `/payroll` has two tabs — "Empleados fijos · pago quincenal" (unchanged) and "Trabajadores independientes · pago diario" (day picker, same local filter/search, own summary cards, consolidated by local). "Generar quincena" only creates payments for FIJOS.
- **Independent worker = daily list + pay**: each day is one `nominas` row with `periodo_inicio = periodo_fin = day` (so PENDIENTE/PAGADO immutability, payment proof, per-local access and live updates all apply), and its list of resold products lives in `nomina_reventas` (producto_id nullable, name/code snapshot, `cantidad`, `precio_lista` = catalog price when the line was added, `precio_vendido`; CHECK `precio_vendido >= precio_lista`). **Pay = the profit over list price**: `Σ cantidad × (precio_vendido − precio_lista)` (`gananciaReventa()`), + bonos − deducciones. The list **does not touch stock**. Selling below list price is rejected. The lines table has **no write policies**: everything goes through the RPC `guardar_pago_independiente(...)` (one transaction: validates, computes the pay from the list, upserts the day, replaces the lines, optionally marks it PAGADO; a PAGADO day is frozen). `inventoryService.guardarPagoIndependiente` wraps it (proof upload first, cleaned up on failure); LocalStorage keeps the lines in `db.reventas` with the same rules.
- **The contador can't read the catalog**, so product lookup for the list goes through the RPC `catalogo_reventa(texto, limite)` (administrador/gerente/contador only; returns id, código, nombre, categoría and precio de venta — never cost or stock; empty text returns nothing; max 60). UI: the pay dialog gains a product search (debounced; Enter with a scanner code adds an exact match), editable cantidad / precio vendido per line with live profit, and is read-only once paid.
- **Contador experience**: `protegerPagina` sends the contador to `/payroll` from every page that doesn't list the role (so login lands there); the sidebar shows only "Nómina" (every other link's `roles` omit it); no tasa chip/dialog, no local switcher, no "no local" banner (`esSinLocal()` = administrador/gerente/contador: no local assigned). Demo account `contador@edwardaccesorios.com` / `contador123`.
- **Migrations**: `0026` (enum `contador`, run ALONE) then `0027`; `0032` (independent workers: tipo, `nomina_reventas`, the two RPCs); `0029` (payment proof column + private bucket); `0030` (live updates: realtime publication); `0028` (optional, idempotent) adds 3 fictitious demo employees (cédulas `V-9000…`, one per local) — set them INACTIVO or ignore them once the real staff is loaded.

### Live updates across devices (Realtime)

Sales, stock entries, payroll payments, the exchange rate, subscriptions, etc. show up on every open screen **without reloading**. `src/lib/realtime.ts`:
- `iniciarTiempoReal()` (called by `protegerPagina` and lazily by the helper) opens ONE Supabase Realtime channel (`postgres_changes`, event `*`) on the tables in `TABLAS_TIEMPO_REAL` — they must be in the `supabase_realtime` publication (migration `0030`, idempotent; **add a table to both when you add a live screen**). Changes arrive **filtered by RLS** (each user only hears about rows they can read: a vendedor gets nothing from payroll; a suspended local goes quiet). The payload is **ignored**: only "which table changed" is used, and the screen re-fetches through the usual `inventoryService`/`auth` functions, so no new data path or permission exists.
- It re-emits `'*'` (refresh everything) when the tab becomes visible, when the connection returns (`online`) and when the channel reconnects, so a sleeping phone catches up.
- **Demo mode** (no Supabase) has no other devices but other *tabs*: the `storage` event on `easystem:db:v1` / `easystem:usuarios` / `easystem:suscripciones` / `easystem:cierres-forzados` feeds the same mechanism (how it was tested locally).
- Screens subscribe with `alCambiarDatos(['ventas', ...], recargar, esperaMs?)`: window event `easystem:datos-cambiaron` `{ tabla }`, debounced (600 ms; reports 2 s) and never two reloads at once (one queued). **Rules for a refresh handler**: re-render lists but keep filters, page and what the user is typing (first load animates, refreshes don't); never rebuild inputs the user is editing.
- Wired up: dashboard (cards, low stock, recent movements, quick search), notifications bell, Productos, POS, Ventas realizadas, Movimientos, Reportes, Servicio técnico, Ingreso de mercancía (only the stock numbers), Nómina, Usuarios, Suscripciones, the exchange rate (`TasaDelDia`) and the account guard.
- **POS**: after a refresh `ajustarCarritoAlStock()` re-points each cart line at the fresh product and lowers/removes lines that no longer have stock (with a visible warning); refreshes wait while any `<dialog>` is open so a total never changes mid-checkout. **Nómina**: if the open payment dialog's payment was paid from another device, it closes with a notice. **Guard**: a `locales`/`perfiles` change (suspension, forced logout, deactivation) triggers `revisar()` at once instead of waiting for the 60 s check.

### Unit codes (one unique code per physical unit)

Every physical unit has its OWN code (migration `0033`, table `unidades_producto`: `producto_id`, `local_id`, `codigo` unique, `estado` DISPONIBLE|VENDIDA, `vendida_en`, `impresa_en`; LocalStorage: `db.unidades` + `db.unidadSeqPorPrefijo`). The code is **PREFIX + 6 digits, consecutive per prefix** (`INF000001`, `INF000002`, `TEC000001`…; **migrations `0007`/`0008`**, which replaced the old EAN-13 `21…` codes). The prefix (2–4 letters A–Z, normally the first 3 letters of the brand) is a column of the PRODUCT (`productos.prefijo_codigo`, chosen in `FormularioProducto`, suggested by `sugerirPrefijo(nombre, categoria, marcas)`: brand as a whole word in the name → iPhone → category → `GEN`); products sharing a prefix share the count. The counters live in `contadores` as `unidad:<PREFIJO>` (`movimientos.ts` reserves a range per prefix per request; going past 999999 gives 409 `prefijo_agotado`). Changing a product's prefix only affects units created afterwards (existing codes are kept). Pure helpers in `utils/codigos.ts`: `construirCodigoUnidad(prefijo, n)`, `esCodigoUnidad`, `esPrefijoValido`, `prefijoDelCodigo`, `normalizarCodigoUnidad` (typing `inf14` = `INF000014`, used by POS/Ingreso/Descargo), `sugerirPrefijo`. **The QR content is exactly that code and the label prints it under the product name** (`htmlEtiqueta` / `svgEtiqueta`). Migration `0008` gave a prefix to the existing products and renumbered the existing units (also `traslado_unidades`; the history JSON — movements, sales, returns — keeps the old codes) and seeded the counters; LocalStorage does the same in `migrarCodigosUnidad` (it rewrites the stored history too). A factory barcode could look like a unit code: the POS falls back to the product lookup when no unit has that code.

- **Product reference (`INF-001`)**: every PRODUCT also has a short human reference `PREFIX-NNN` (hyphen + 3 digits, 4+ past 999) with the SAME prefix as its piece codes, consecutive per prefix (`productos.referencia`, unique; counters in `contadores` as `producto:<PREFIJO>`; migrations `0009` column + unique index and `0010` idempotent backfill by prefix and creation order). It is assigned by `crearProducto` / `crearProductosLote` (`reservarReferencias` reserves the numbers before inserting: a failed insert leaves a gap, never a duplicate) and **never changes** (changing the prefix later only affects new pieces; `actualizarProducto` ignores `referencia`). The EAN-13 `codigo_barras` stays for factory packaging and duplicate checks and is still editable in the form, but lists show `codigoVisible(p)` (`utils/codigos.ts`: reference, else barcode) and every search also matches the reference. `normalizarReferencia('inf-7')` → `INF-007` is used by the POS and Ingreso for exact matches (a reference in the POS unit field adds any unit of that product, like a factory code). **`normalizarCodigoUnidad` does NOT accept a hyphen/space any more** (`inf14` → `INF000014` still works) so a piece abbreviation can never be confused with a product reference. LocalStorage parity: `db.referenciaSeqPorPrefijo`, `asignarReferenciaLocal`, `migrarReferencias` (numbers existing products once).

- **Units move only with stock movements** (never written directly: RLS gives `authenticated` SELECT only, via `local_accesible(local_id)`). A BEFORE INSERT trigger on `movimientos_inventario` (`preparar_unidades_movimiento`) does it: ENTRADA of N creates N units (or, if the movement lists `unidad_codigos`, reactivates those VENDIDA units — returns — and creates the rest); SALIDA marks VENDIDA the listed `unidad_codigos` (scanned units; must be DISPONIBLE in that local and product, else the whole movement is rejected) and completes the rest FIFO (oldest first). The movement's `unidad_codigos` column ends up with ALL the codes it moved, so `registrarMovimiento` returns them. Invariant: DISPONIBLE units = `inventario_local.stock_actual` per product/local. LocalStorage mirrors it in `moverUnidadesLocal` (also used by the CSV importer's `mover`); `migrarUnidades` gives a code to the stock that already existed (the SQL migration does the same, idempotently).
- **Sales snapshot the units**: `VentaItem.unidades` (codes that left) is saved in `ventas.items`; `registrarDevolucion` returns the SAME units (excluding those already returned in earlier returns), replacement items record theirs, and service-order parts keep them too. Sales/orders made before 0033 have none: their returns create new units.
- **Service API** (`inventoryService`): `listarUnidades({ productoId, estado, sinImprimir, codigos })` (active scope; needs connection with Supabase, no offline copy), `obtenerUnidadPorCodigo`, `marcarEtiquetasImpresas` (RPC `marcar_unidades_impresas`: administrador/gerente/encargado). Offline (Supabase mode) a unit code cannot be resolved: the POS tells the cashier to search by name, and a name-search sale is queued like before (units are assigned FIFO when it syncs).
- **POS: UN solo campo arriba** (`#pos-codigo`, sin título ni textos explicativos; `buscador` en el script es el mismo elemento): escanear (lector USB o cámara), escribir el código de una etiqueta o buscar por nombre, categoría o modelo (la lista se filtra al escribir, con 120 ms de pausa). Con **Enter**, `pareceCodigo()` decide: código completo de etiqueta (INF000026), código largo de barras, código/referencia exacta de un producto, o abreviado ("inf14") solo si no coincide con ningún nombre y su prefijo existe → `agregarPorCodigo`; si no, es una búsqueda y Enter no hace nada. Ya no hay teclado numérico en el teléfono (el campo también recibe nombres). Debajo queda solo el botón **Seleccionar código**.
- **POS** (`ventas.astro`): the FIRST field is "Código de la unidad" (reader + Enter, or the camera via `data-abrir-escaner`); right below, **Seleccionar código** opens a dialog (product → list of its available unit codes, "Aún sin etiqueta impresa" flagged) for when nothing can be scanned; name/model search is below that. A unit-shaped code adds THAT unit (errors: unknown, already sold, other local, already in the cart); a product code (factory barcode) still adds any unit. Cart lines are per product with `unidades: string[]` chips (✕ removes one unit); `revalidarUnidadesCarrito` drops units another device sold (realtime `unidades_producto`, and after a rejected sale).
- **Ingreso** prints ONE label per unit: "Registrar ingreso" stores the created codes in the lote line (`unidades`) and the label count follows them; "Imprimir etiquetas" prints the line's new units first, then the oldest units still without a label (`impresa_en` null; the line shows "N sin etiqueta"), then marks them printed. It asks to register the ingreso first if a line still has units to enter. After the migration every existing unit is "sin etiqueta": print and stick them product by product with quantity 0. Scanning a unit label in Ingreso just locates its product in the lote.
- `unidades_producto` is in `TABLAS_TIEMPO_REAL` and the realtime publication (added at the END of 0033, after the backfill, so loading thousands of units doesn't flood listeners).

### Pendientes y promotores (Local Vidrios; migración 0018)

En el **Local Vidrios** el módulo "Modelos de teléfono" está oculto (`ocultoEnLocal` de `navLinks.ts` ahora acepta varios tipos de local) y en su lugar sale **Pendientes** (`pages/pendientes.astro`, `soloTipoLocal: 'vidrios'`; administrador, gerente y encargado; el administrador/gerente en "Todos" también lo ven). Ahí se anota (1) la **mercancía** que un promotor se llevó y vendrá a pagar y (2) las **comisiones** de promotores por ventas con precio de promotor. Todo se ve también en **Nómina → Trabajadores independientes** (sección "Promotores", `pn-sec-promotores`) para administrador, gerente y contador.

- **Tablas** (migración `0018`): `promotores` (directorio: cédula única, nombre, apellido, teléfono, **banco receptor**), `pendientes` (`tipo` MERCANCIA|COMISION, `estado` PENDIENTE|PAGADO|ANULADO, monto USD, `promotor_id` nullable, `venta_id`/`venta_folio` en las comisiones, cierre con nota) y `ventas.promotor_banco`. Un pendiente cerrado no cambia.
- **Directorio**: `servicios/promotores.ts` + `/api/promotores` (lista con lo que se le debe, crear, editar, buscar por cédula). Lo ven y agregan administrador, gerente, encargado y contador. "**+ Agregar promotor**" está en Pendientes, en Nómina y en la ventana de mercancía (`components/promotores/FormularioPromotor.astro`, evento `easystem:abrir-promotor` / `easystem:promotor-guardado`). Los datos de un pendiente se leen del directorio, así un banco corregido vale para lo que aún se debe.
- **POS**: la ventana de precio de promotor pide además **Banco receptor** (lista `BANCOS_SUGERIDOS`, validado en `utils/promotor.ts`). Al escribir una cédula de ≥ 5 dígitos busca el promotor (`buscarPromotorPorCedula`, 350 ms de pausa) y **completa solo los campos vacíos** (nombre, apellido, teléfono, banco) con el aviso "Promotor registrado". El banco NO entra en la `clave` de la autorización firmada (cédula|nombre|dígitos): cambiarlo no invalida la autorización.
- **Comisión automática**: `guardarVenta` agrega al MISMO batch de la venta (`sentenciasComisionPromotor` en `servicios/pendientes.ts`) el alta/actualización del promotor (si trae cédula) y un pendiente COMISION con el monto de `comision`. Sin cédula también se anota (queda sin promotor: en Pendientes tiene "Asignar promotor"). En modo "Precio del local" no hay comisión.
- **Permisos** (matriz en `matriz-roles.test.ts`; el servicio vuelve a comprobar y un pendiente de otro local responde 404): anotar mercancía = administrador/gerente/encargado de ese local; **pagar una comisión** = administrador, gerente o contador (desde Nómina); anular una comisión = administrador/gerente; pagar/anular mercancía = gerencia del local. El vendedor y el técnico no ven nada. `POST /api/pendientes`, `/api/pendientes/:id/cerrar`, `/api/pendientes/:id/promotor`.
- **Monto en Bs y datos para el pago móvil** (`utils/pagoMovil.ts`): todo monto de Pendientes, de la lista de promotores (Pendientes y Nómina) y de la ventana «Marcar pagada» se ve en dólares y, debajo, en **Bs al cambio de hoy** (`tasaActual`; la comisión está en dólares, así que sigue al dólar: el monto en Bs cambia con la tasa; sin tasa solo sale el $, p. ej. para el contador). Cada promotor con datos y cada comisión por pagar llevan botones **Copiar datos** (nombre, cédula, teléfono, banco y monto en Bs y $), **Cédula** y **Teléfono** (solo dígitos) y **Monto Bs** (`3402,00`, coma decimal y sin miles): el gerente los pega en el pago móvil del banco. `activarBotonesCopiar(raiz)` maneja los `data-copiar` (portapapeles con respaldo `execCommand`). Test: `tests/cliente/pago-movil.test.ts`.
- **Borrado de ventas**: eliminar ventas / resetear ventas / resetear reportes quitan sus comisiones **no pagadas** (`sentenciasBorrarComisiones`); las ya pagadas se conservan.
- **Tiempo real**: `pendientes` (por local) y `promotores` (directorio global) se avisan desde `servicios/cambios.ts` (la nómina también los oye) y en `TABLAS_TIEMPO_REAL`.
- **Demo (LocalStorage)**: `db.promotores` y `db.pendientes` con las mismas reglas (`anotarComisionPromotorDemo`). Tests: `tests/server/pendientes-promotores.test.ts`, `tests/cliente/pendientes-promotores.test.ts`, filas en `matriz-roles` y `navLinks.test.ts`.
- **Instalación de vidrios** (solo en el POS del Local Vidrios; sin migración, va dentro del JSON de `ventas.items`): cada línea del carrito tiene el botón **«+ Instalación»** (`#pos-instalacion`) con tres opciones: sin instalación, **la instala el local** (ingreso de la tienda) o **la instala el promotor**. El precio es **por unidad** y viene en $3 (`INSTALACION_PREDETERMINADA_USD`, editable por vidrio, máx. $100). Se guarda en la línea como `instalacion_por` (`LOCAL`|`PROMOTOR`) e `instalacion_usd`, **suma al total** de la venta (`utils/instalacion.ts`: `totalLinea`, `totalDeItems`, usados por el POS, el ticket y su imagen, el historial y `registrarVenta`) y el cliente paga todo a la tienda. Si la instala el promotor, esa parte es dinero que la tienda le entrega: el servidor la **suma a `ventas.comision`** y al pendiente COMISION (que explica por separado el precio y la instalación; `instalacionDelPromotor`, `descripcionPendiente` en `servicios/ventas.ts`). El promotor sale de la autorización del precio si la hay (un solo promotor por venta) y, si no, de los datos que se piden en esa misma ventana (cédula, nombre y apellido; con autocompletado por cédula): viajan en `NuevaVenta.promotor` / `DatosVenta.promotorInstalacion`, sin contraseña (la instalación no cambia el precio del catálogo). Instalación por el local no genera pendiente. Con «precio del local» la instalación del promotor funciona igual. Tests: `tests/server/instalacion-vidrios.test.ts`, `tests/cliente/instalacion.test.ts` y el caso del demo en `tests/cliente/pendientes-promotores.test.ts`. **Límites**: una devolución reembolsa solo el producto (no la instalación); Reportes cuenta el ingreso por producto sin la instalación (el total de la venta y el cuadre de caja sí la incluyen); el servidor sigue confiando en el total que manda el cliente; el precio de instalación no pide contraseña.
- **Límites conocidos**: la mercancía pendiente **no mueve el stock** (es solo un registro de deuda; si se quiere descontar, hacer una baja/venta aparte); una devolución no revierte la comisión; pagar una comisión no genera un pago en Nómina (queda registrado en Pendientes con nota); un promotor no se borra (solo se edita).

### Control por cantidad (vidrios sencillos baratos, sin código por pieza)

Para mercancía de centavos (vidrios sencillos del Local Vidrios) una etiqueta por pieza no vale la pena. `productos.control_por_cantidad = 1` (migración `0017`, columna + tabla `mermas`) hace que el producto se controle SOLO por cantidad: no crea filas en `unidades_producto`, el stock es el número de `inventario_local` y las ENTRADA/SALIDA/BAJA solo mueven ese número. Los vidrios con etiqueta ($5 en adelante) no cambian.

- **Regla de precio**: solo puede ser por cantidad un producto de **menos de $3** (`PRECIO_MAXIMO_POR_CANTIDAD`, `errorPrecioPorCantidad` en `utils/controlPorCantidad.ts`). Se exige al crear/editar/alta rápida/importador. Cambiar entre "por cantidad" y "con etiqueta" solo con el stock en 0 en todos los locales. Una ENTRADA con `unidad_codigos` a un producto por cantidad se rechaza.
- **Una sola etiqueta por pila**: en Ingreso se imprime UNA etiqueta por modelo con el código del PRODUCTO (EAN-13 `codigo_barras` / referencia), no por pieza (las copias por defecto son 0; se piden a mano). Al escanearla en el POS se suma 1 unidad (el POS ya hacía eso con códigos de producto); la cantidad se edita en el carrito y la venta guarda `movimiento_id` en vez de códigos de pieza. El ingreso registra la cantidad sin etiquetas por pieza. Se cuenta por cantidad con la hoja de Inventario "por producto".
- **Vidrio defectuoso en una venta** (`VentaItem.danados` + `danados_motivo`, nota opcional): se cobra solo lo que sirvió y las piezas defectuosas salen del stock como BAJA en la MISMA petición (`POST /api/movimientos/con-merma`, `registrarSalidaConMerma`; atómico) y quedan en `mermas` (quién, motivo opcional, origen VENTA/DESCARGO, quién autorizó). El botón **solo lo ven encargado/gerente/administrador** (el vendedor recibe 403). **3 o más defectuosas en una venta (`UMBRAL_CLAVE_DANADOS`) piden la contraseña de un gerente o administrador** (`POST /api/ventas/autorizar-danados`, `autorizarDanados` en `servicios/autorizaciones.ts`: firma HMAC de 20 min atada a quien vende, el local y la cantidad; mismo 403 genérico y tope de 5 fallos/15 min que las demás autorizaciones; la clave de un encargado no vale). Necesita conexión (no se encola).
- **Descargo → "Bajas por cantidad"** (`components/mercancia/Descargo.astro`, `POST /api/mermas` y `GET /api/mermas`, `lib/db/mermas.ts`): baja de N piezas de un producto por cantidad con motivo opcional; queda en la lista de mermas. No hay "Revertir" (se reingresa la cantidad). Los traslados entre locales por cantidad NO están implementados.
- **Eliminar/Resetear ventas** devuelven al stock también las piezas por cantidad (cobradas y botadas) y borran sus mermas. `mermas` está en `TABLAS_LOCAL` (servidor) y `TABLAS_TIEMPO_REAL` (cliente).
- **Demo (LocalStorage)**: mismas reglas (`db.mermas`, `moverCantidadDemo`, `danadosDemo`). Tests: `tests/server/control-por-cantidad.test.ts`, `tests/cliente/control-por-cantidad.test.ts` y filas en `matriz-roles`.
- **Límites conocidos**: la suma ≥3 se comprueba por petición con la cantidad que declara el cliente (`guardarVenta` no la recalcula); el tope de $3 solo se exige al marcar el producto, no si después se sube el precio; los productos con etiqueta ya existentes y los duplicados no se tocan.

### Reportes y cuadre — daily cash reconciliation (cuadre de caja)

The page `/reportes` (nav "Reportes y cuadre"; **administrador and gerente only** — the encargado does NOT see reports) keeps the financial reports and adds the button **Cuadre de caja del día**, which opens `components/reportes/CuadreCaja.astro` (event `easystem:abrir-cuadre`). The **encargado** gets his own nav link "Cuadre de caja" → `pages/cuadre.astro`, the same component with `modo="pagina"` (embedded, always visible, loads today's cuadre on entry; no reports at all). Both modes have **Imprimir / PDF** (`imprimir()` builds a temporary `#cuadre-impresion` container with the cobros table, differences, notes, every photo and signature lines, hides the rest of the page in `@media print`, same technique as the labels). Migration `0034`; table `cuadres_caja` (LocalStorage: `db.cuadres`).

- **One cuadre per local and day** (UNIQUE local_id + fecha), states ABIERTO (draft) → CERRADO. `esperado` = what the system says each payment type collected that day (`esperadoDelDia`, same net-of-vuelto/refunds math as `resumirPorMetodo`; sales + that day's returns of ONE local, `listarVentas/listarDevoluciones({ localId })` bypass the active scope); `contado` = what was declared (Bs for the `BS_*` types, $ for the rest); `fotos` = `[{ tipo, path }]`. Pure rules (photo types, differences, "can it be closed?") live in `utils/cuadre.ts`.
- **Photos** (types PAGO_MOVIL, BINANCE, EFECTIVO, CIERRE_PUNTO; several per type; shrunk to 1280 px in the browser): private bucket `cuadres-caja`, path `<local_id>/<aaaa-mm-dd>/<tipo>-<ts>-<n>.jpg`, viewed through 1-hour signed URLs (`urlFotoCuadre`). A photo type is **mandatory to close** when the system expected money in the payment types it backs, and every payment type with expected money needs a counted amount (`problemaParaCerrar`). Differences do NOT block closing (they're shown "Sobra/Falta" and can be explained in notes).
- **Roles**: encargado only his own local (the window shows it fixed); administrador and gerente pick any local and see chips with the state of the day in every local (Sin cuadre / Borrador / Cerrado · cuadra / con diferencia). Vendedor/técnico/contador: nothing (RLS: `es_gerencia() and local_accesible(local_id)`; the service re-checks in `accesoCuadre`).
- **Closed = immutable** (trigger `preparar_cuadre_caja`; closing asks for a second click): the closed row keeps the `esperado` snapshot, uploads/deletes of photos are blocked in storage policies (`cuadre_foto_editable`), and only administrador/gerente can **reabrir** it (`reabrirCuadre`). Service: `calcularEsperadoCuadre`, `listarCuadresDelDia`, `obtenerCuadre`, `guardarCuadre`, `reabrirCuadre`. Needs a connection (not queued). `cuadres_caja` is in `TABLAS_TIEMPO_REAL` + the realtime publication; the window refreshes silently unless something is being typed.

### Perfil y contraseña propia (cualquier rol)

El círculo con las iniciales del menú lateral (con el nombre, `#nav-perfil` en `Sidebar.astro`) abre el **perfil** (`components/layout/PerfilUsuario.astro`, dentro de `DashboardLayout`; evento `easystem:abrir-perfil`): nombre, rol, correo, local ("Todos los locales" para administrador/gerente/contador), cuándo empezó la sesión y cuándo se creó la cuenta, **Cambiar mi contraseña** y Cerrar sesión. **Todos los roles** (vendedor, encargado, técnico, contador incluidos) pueden cambiar la suya; ya no depende de un gerente.

- **Servidor**: `POST /api/cuenta/clave` `{ actual, nueva }` (`cambiarMiClave` en `servicios/usuarios.ts`): exige la clave actual (400 `clave_actual_incorrecta`), nueva de ≥ 8 y distinta (`clave_corta`/`clave_igual`), **cierra las demás sesiones de la cuenta** (conserva la actual por `Sesion.sesionId`) y quita la marca de clave temporal. 5 fallos seguidos → 429 por 15 min (tabla `rateLimit`, clave `clave-propia:<userId>`, un acierto la borra). Como el resto de la API, un local suspendido da 403 (`alcanceDe`; el contador, `alcanceNomina`). Fila en `matriz-roles` (permitidos: todos); `tests/server/clave-propia.test.ts`.
- **Clave temporal obligatoria** (migración `0016`, `perfiles.debe_cambiar_clave`): la cuenta que crea un administrador/gerente (`crearUsuario`) y la clave que uno le restablece a OTRA persona (`cambiarClaveUsuario`, id ≠ actor) quedan marcadas; la que uno se fija a sí mismo la quita. Las cuentas que ya existían quedan en 0 (no se bloquea a nadie de golpe). Mientras esté marcada `conSesion` responde **403 `debe_cambiar_clave` a todo salvo `/api/cuenta/clave`** (`/api/cuenta/estado` no usa `conSesion` y avisa con `usuario.debe_cambiar_clave`). En la interfaz `protegerPagina` se detiene (la página no carga) y `PerfilUsuario` se abre sola, sin poder cerrarse (Esc y fondo bloqueados; solo "Cerrar sesión"); al cambiarla recarga. La copia de la sesión para trabajar sin conexión no lleva la marca (el servidor la exige igual). `crearUsuarioInterno` acepta `debeCambiarClave` (el script del primer administrador no la pone).
- **Demo (LocalStorage)**: mismas reglas (`cambiarMiClave` compara la clave en texto plano; `debe_cambiar_clave` en `easystem:usuarios`). `tests/cliente/clave-propia.test.ts`.
- **Sin verificación en dos pasos** (decisión del dueño, de momento): queda pendiente, solo para administrador y gerente (TOTP con Better-Auth + códigos de respaldo + script de desbloqueo).

### Presencia ("Tiempo real"): quién está usando el sistema

Pantalla `/admin/monitoreo` (nav "Tiempo real", **solo administrador**; el gerente no la ve): tabla de conexiones con 🟢 **En línea** (último latido < 45 s), 🟡 **Inactivo** (45 s a 2 min: normalmente una pestaña en segundo plano) y 🔴 **Desconectado** (> 2 min, o salió), contador "Usuarios activos ahora" (= los En línea), filtros por estado, buscador y "Cerrar sesión forzada" (reutiliza `cerrarSesionForzada`; nunca la propia). Muestra nombre, correo, rol, local/sede (los roles sin local fijo informan el que miran en el selector; el resto, el de su perfil: no se puede declarar otro), pantalla actual, dispositivo/IP y hora del último latido. Lista a quien se vio en las últimas 24 h.

- **Latido** (`src/lib/presencia.ts`, lo inicia `protegerPagina`): uno al entrar y luego cada 30 s **solo con la pestaña visible** (más uno al volver a verla o al recuperar la red), por `navigator.sendBeacon` (cuerpo `{ruta, local_id}`, ~50 bytes; cae a `fetch` con `keepalive`). `POST /api/presence/heartbeat` (cualquier rol con sesión) responde **204 sin cuerpo**, tolera cuerpos vacíos/raros y, como el resto de la API, da 403 a una cuenta de un local suspendido (el contador pasa por `alcanceNomina`). Al cerrar sesión (`cerrarSesion` espera el aviso) o la pestaña (`pagehide`) manda `{salir:true}`.
- **Almacén**: tabla `presencia` (migración `0011`; una fila por usuario: `last_seen_at`/`salio_en` en ms, `ip`, `dispositivo`, `local_id`, `ruta`; cae con el usuario). El latido es un **upsert condicional**: solo escribe si pasaron > 10 s desde el anterior (o si había avisado que salía), así D1 no cuenta escrituras de más. **No usa la tabla `cambios`** (nadie debe enterarse de cada latido): la pantalla consulta `GET /api/admin/active-users` cada 10 s mientras se ve y, entre consultas, sigue moviendo los segundos y los estados sola. El estado NO se guarda: `calcularEstado` (`utils/presencia.ts`, compartido por servidor, pantalla y demo) lo deduce al leer.
- **Salida con gracia**: cambiar de pantalla "sale" de una página y entra en la siguiente; la salida solo cuenta si pasan 8 s (`GRACIA_SALIDA_S`) sin un latido nuevo, que la borra. Con varias pestañas, cerrar una puede mostrar al usuario desconectado hasta el siguiente latido de otra (≤ 30 s).
- **Limpieza**: `limpiarPresencia` borra lo no visto hace > 7 días; corre sola en ≈ 2 % de los latidos y a mano con `npm run presencia:limpiar` (D1 remota).
- **Demo (LocalStorage)**: `easystem:presencia`; solo se ven las pestañas del mismo navegador. Al agregar una pantalla con latidos nuevos no hace falta tocar `realtime.ts`.
- Tests: `tests/server/presencia.test.ts`, `tests/cliente/presencia.test.ts`, y las dos rutas en `matriz-roles.test.ts`.

### Rendimiento en redes débiles (qué hay y por qué)

- **Lecturas con ETag** (`conSesion` en `src/server/http.ts`): todo GET que devuelve un objeto sale con `ETag` (SHA-256 del JSON), `Cache-Control: private, no-cache` y `Vary: Cookie`; con `If-None-Match` igual responde **304 sin cuerpo**. El navegador lo hace solo (`fetch`): no hay código de cliente. Las escrituras y los errores no llevan ETag. `tests/server/cache-condicional.test.ts`.
- **Menús sin 307**: `build.format: 'file'` en `astro.config.mjs` (páginas `ventas.html`, no `ventas/index.html`): `/ventas` responde 200 directo; con carpetas Cloudflare redirigía a `/ventas/` en cada navegación. `/ventas/` (con barra) ahora redirige a `/ventas`.
- **Una sola petición de estado al entrar**: `/api/cuenta/estado` trae la sesión Y el estado de la cuenta; `estadoDeEntrada()` (auth.ts) reutiliza esa respuesta (una vez) en `protegerPagina`. Las revisiones periódicas siguen consultando con `obtenerEstadoCuenta()`. `listarProductosCrudos` comparte una sola petición en vuelo entre quienes piden el catálogo a la vez.
- **Miniaturas de fotos de producto** (solo modo servidor): al guardar una foto, `guardarImagenProducto` sube también una miniatura de ~190 px (`crearMiniatura`, `PUT /api/archivos/producto/:id?miniatura=<url de la foto>`, `subirMiniaturaProducto`) con el mismo nombre + `-m` y la misma extensión (`<ts>-m.webp`). `htmlMiniatura` pide la miniatura (`urlMiniatura`), cae a la foto grande con `onerror` si no existe (fotos anteriores; el 404 se recuerda 1 h) y guarda la grande en `data-grande` (el visor `VisorImagen` la usa al ampliar). Borrar una foto borra también su miniatura. Las fotos de producto prefieren **WebP** (`reducirImagen(..., { preferirWebp: true })`, cae a JPEG si el navegador no lo crea). Cloudflare Image Resizing (`/cdn-cgi/image`) NO sirve en `*.workers.dev`: haría falta un dominio propio en Cloudflare.
- **Service worker** (`public/sw.js`, registrado en `DashboardLayout` solo en producción): `/api/*` nunca pasa por él; `/_astro`, `/img` e íconos primero desde la caché; las páginas HTML primero la red (3 s de plazo) y, si falla o tarda, la última copia → la app abre sin conexión. Subir `VERSION` en sw.js borra las copias viejas.
- **`public/_headers`**: `/img/*`, logo e íconos 1 semana; `/sw.js` `no-cache`. (`/_astro/*` ya era `immutable`; HTML, JSON y estáticos salen comprimidos con Brotli desde Cloudflare.)
- Lista de `/api/productos` y `/api/modelos` ya no envía `created_at` de los modelos (el cliente no lo usa). **No se pagina el catálogo en el servidor a propósito**: el POS necesita buscar sobre todo el catálogo (también sin conexión); el ahorro de bytes viene de ETag/304 + miniaturas. Las tablas largas ya pintan por páginas (25 filas) en el navegador.

### UI conventions worth knowing before touching layout

- **Brand**: the palette comes from the company logo (`public/logo.png`; favicon set: `favicon.ico`, `favicon-32.png`, `apple-touch-icon.png`). Colors are Tailwind tokens in `src/styles/global.css` — `brand-*` (blues) and `accent-*` (the logo's cyan); never hardcode hex colors in pages (the Chart.js colors in `reportes.astro` are the only exception, since canvas can't read CSS tokens). `.bg-marca` / `.texto-marca` are the logo gradient.
- **Animations** live in `global.css` (keyframes + `.anim-*` classes) and are triggered from `src/utils/animaciones.ts` (`animarLista`, `reanimar`, `contarHasta`). They use the individual `translate`/`scale`/`rotate` properties so they don't clobber Tailwind transforms, and everything respects `prefers-reduced-motion`. Use `animarLista` only on the *first* render of a list — never on search-as-you-type re-renders, or rows flicker on every keystroke.

- Sidebar is a mobile drawer (`-translate-x-full`/`translate-x-0`, `lg:translate-x-0` pinned on desktop), toggled by the Header's hamburger button. POS (`ventas.astro`) adds a fixed bottom bar with total + "Cobrar" so checkout doesn't require scrolling on small screens (it carries `mb-0`: its `space-y` parent adds a 24px bottom margin to non-last children that otherwise lifts a `fixed bottom-0` bar off the screen edge).
- Ticket/report printing uses `window.print()` with Tailwind `print:` utilities to hide sidebar/header/forms, not a separate print view.
